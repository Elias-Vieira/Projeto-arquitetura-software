Atividade Prática — Garagem de Veículos
Arquitetura de Software • ESW430 • UniRV
1. Objetivo
Cada grupo vai construir o sistema Garagem de Veículos, com cadastro de pessoas, cadastro de veículos e uma página inicial de Reservas, onde um veículo é vinculado a uma pessoa por um período.
A atividade coloca em prática a Aula 3: MVC + padrão Repository + Injeção de Dependência, seguindo os princípios SOLID. A regra central é a mesma dos slides: o Controller nunca deve saber como os dados são salvos.

3. Arquitetura obrigatória
Cada entidade precisa de cinco arquivos com estes nomes: Model, Interface do repositório, Repositório, Controller e View de formulário. O caminho dos dados é sempre View → Controller → Interface → Repositório → arquivo JSON.

Arquitetura exigida · exemplo com Pessoa
Se amanhã o JSON virar banco de dados, só o PessoaRepository muda: Controller e Views continuam iguais.

Proibido
Ler ou gravar o arquivo JSON dentro do Controller (File.ReadAllText, ObjectMapper, FileWriter etc.).
Criar o repositório com new PessoaRepository() dentro do Controller: ele chega pelo construtor.
Manter uma lista static de dados no Controller (o “design ruim” da Aula 3).
Colocar regra de negócio ou acesso a dados dentro da View.
4. SOLID aplicado ao projeto
Cada princípio tem que aparecer no código, e não só no README.
Princípio
Como deve aparecer no projeto
S — Responsabilidade Única
Model guarda dados e validações. Repository só lê e grava o JSON. Controller só recebe a requisição, chama o repositório e escolhe a View.
O — Aberto/Fechado
Trocar o JSON por banco de dados (EF Core ou JPA) deve exigir só uma nova classe de repositório, sem mexer no Controller nem nas Views.
L — Substituição de Liskov
Qualquer classe que implemente IPessoaRepository (JSON, memória ou banco) precisa funcionar no Controller sem ajuste.
I — Segregação de Interfaces
Uma interface por entidade (IPessoaRepository, IVeiculoRepository, IReservaRepository), cada uma só com os métodos que usa.
D — Inversão de Dependência
O Controller depende da interface, recebida pelo construtor. Quem entrega a implementação concreta é o container de DI.

Página inicial: Reservas
Ao abrir o sistema, o usuário cai direto em Reservas. No C#, defina a rota padrão como {controller=Reserva}/{action=Index}/{id?} no Program.cs; no Java, use @GetMapping("/") no ReservaController.
Arquivos: Reserva, IReservaRepository, ReservaRepository, ReservaController e a View Reserva/Index (um ReservaForm separado é opcional), com dados em reservas.json. O Model Reserva tem, no mínimo: Id, VeiculoId, PessoaId, DataInicio e DataFim.
A página de Reservas deve:
Listar as reservas com veículo (placa e modelo), pessoa (nome) e período.
Criar uma reserva escolhendo veículo e pessoa em listas (select) carregadas dos repositórios, mais data de início e fim.
Editar o período de uma reserva e cancelar (excluir) uma reserva.
Mostrar cada veículo como Disponível ou Reservado na data de hoje. O status pode ser calculado a partir das reservas (recomendado) ou gravado no veículo.
Regra de negócio: um veículo, uma pessoa por período
Um veículo não pode ter duas reservas com períodos que se sobrepõem. Duas reservas do mesmo veículo entram em conflito quando:
novaInicio <= existenteFim  E  novaFim >= existenteInicio
Reserva existente
Nova reserva (mesmo veículo)

16/10 a 20/10

10/10 a 15/10

Bloqueada: 14 e 15 se sobrepõem
10/10 a 15/10
15/10 a 17/10
Bloqueada: o dia 15 já está reservado
10/10 a 15/10
01/10 a 31/10
Bloqueada: engloba o período inteiro
Regras complementares:
DataFim não pode ser anterior a DataInicio.
Pessoa e veículo precisam existir nos seus repositórios.
Ao editar, a reserva não conflita com ela mesma: ignore o próprio Id na verificação.
Quando bloquear, mostre uma mensagem na tela. A aplicação não pode quebrar.
A verificação fica fora do Controller: um método como ExisteConflito(veiculoId, inicio, fim, idIgnorado) no IReservaRepository ou uma classe ReservaService. O Controller só chama e exibe o resultado.
Desafios extras (opcionais)
Impedir a exclusão de pessoa ou veículo com reserva em andamento ou futura.
Filtrar reservas por pessoa ou por período.
Testar o Controller com um repositório falso (mock), como visto na Aula 3.
